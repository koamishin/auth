# Multi-session accounts

Multi-session lets a browser hold several signed-in accounts at once and switch between them without entering a password again. Signing in as another account does not replace the one already there: both stay available, and the browser remembers which one is active.

## How multi-session works

Every completed sign-in — password, passkey, emailed code, social connection, or invitation — registers the account on the browser. A browser can hold up to **8 accounts**; the oldest are dropped beyond that.

Each registered account holds a **switch token**:

| Property      | Description                                                                                                        |
| ------------- | ------------------------------------------------------------------------------------------------------------------ |
| Storage       | An encrypted, `HttpOnly` cookie on the browser. The raw token never reaches the server's database.                 |
| Server record | A SHA-256 hash per account, in `multi_session_accounts`. A leaked database cannot be used to switch into accounts. |
| Lifetime      | 30 days. Every new sign-in mints a fresh token, so actively signing in keeps access alive.                         |
| Scope         | Per account. A device familiar to one account can still be new to another.                                         |

Exactly one account is active at a time. The rest stay signed in in the background and can be switched to instantly.

## Sign in to another account

To add an account to the current browser:

1. Open the account switcher and select **Add account**, or open `/login?add=1`.
2. Sign in as usual.

The sign-in form notes that signing in adds another account to this browser. Completing it switches to the new account while the previous one remains available. Without the `add` parameter, the sign-in page keeps redirecting signed-in users away as usual.

## Switch accounts

To switch, select an account from the account switcher. The browser signs in as that account and returns to the dashboard.

Two behaviors are deliberate:

- **No state leaks between accounts.** The previous account's session data is dropped before the switch, so intended URLs, verification flags, and similar state never carry over.
- **The session's lifetime limits are kept.** The inactivity timeout and maximum lifetime pinned to the session survive a switch, matching the rule that changing session settings only affects sessions created afterwards.

> A switch re-establishes an ordinary session. It does not carry over a multi-factor check: an application that requires MFA asks again after switching, because the switch itself proves nothing. Factor verification ages reset for the same reason — see [session tokens](session-tokens.mdx).

## Signing out

| Action                       | Effect                                                                                                                                    |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **Log out**                  | Signs out the current account and removes it from this browser. Other accounts remain and are offered on the sign-in page to continue as. |
| **Remove** (× on an account) | Drops that account from this browser without touching the current session. Removing the current account also ends the session.            |
| **Sign out of all accounts** | Clears the registry and ends the session entirely.                                                                                        |

Signing out of one account therefore leaves the others signed in — that is what makes _Continue as_ work.

## When switch access is revoked

- Signing out of an account removes its switch token on that browser.
- Revoking a user's sessions (`revokeAllSessions()`) — which banning a user also performs — deletes every switch token the user holds, on **every** browser. A revoked account cannot be switched back into.
- Banned accounts are refused at switch time even if a token is still present.
- Expired tokens are refused and pruned; the account must sign in again.

## Where the switcher lives

- **Admin panel**: the _Accounts_ menu in the topbar, next to the user menu.
- **Portal**: the user menu lists the signed-in accounts, with _Add account_ and _Sign out of all accounts_.
- **Sign-in page**: _Continue as_ offers the remaining accounts after signing out of one.

## Endpoints

The switcher drives three session routes. They are CSRF-protected POSTs reachable while signed out as well as signed in: the registry cookie is what authorizes a switch.

| Endpoint                      | Body      | Effect                                           |
| ----------------------------- | --------- | ------------------------------------------------ |
| `POST /accounts/switch`       | `user_id` | Sign the browser in as one of its held accounts. |
| `POST /accounts/remove`       | `user_id` | Drop one account from this browser.              |
| `POST /accounts/sign-out-all` | —         | Clear the registry and end the session.          |

## Current limits

- Hosted application sign-ins register on the browser like any other sign-in, but switching in the middle of an application's hosted flow is not supported; switch outside the flow instead.
- The [PHP](../../packages/koamishin-auth-php/README.md) and [JavaScript](../../packages/koamishin-auth-js/README.md) clients do not expose account-switching helpers yet; the endpoints above can be called directly. Both clients support [session tokens](session-tokens.mdx).
