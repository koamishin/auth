# Security

## Protect administrator access

Fortify is configured for registration, password resets, email verification, two-factor authentication and passkeys. The Filament admin panel has its own authentication configuration and restricts access to users with `super_admin`; the application also gives that role a global Gate override. Review role assignments and protect privileged accounts with appropriate authentication factors. The first-run wizard accepts an administrator password of at least eight characters; choose a strong unique password.

The default seeder creates known-password accounts, including a super administrator. Do not run it on an exposed instance; if used, secure or remove the accounts immediately. Rerunning it also assigns roles to preexisting users with the seeded email addresses. Restrict access and retain a secured super administrator when removing accounts, because removing the last super administrator reopens `/setup`. Restrict access to an uninitialized deployment until `/setup` is complete. The setup wizard is locked by the existence of a `super_admin`, so protect role administration and recover access deliberately.

## Protect configuration and data

Protect `.env`, database credentials, OAuth client secrets, `APP_KEY`, and `storage/oauth-private.key`. Use HTTPS and appropriate proxy, cookie and session settings. Set a correct `APP_URL` for passkeys. Configure mail delivery and review registration and account recovery policies for your deployment. The application logs user activity; review log access and retention to avoid exposing sensitive information.

Application sign-in flows use the Portal's browser session to store short-lived transaction state. When simultaneous requests can write the same session, configure a shared, lock-capable cache and set `block` to `true` in `config/session.php` to enable Laravel's session blocking; otherwise concurrent browser requests can overwrite session data. A flow expires after ten minutes, so start again from the application if authentication or recovery takes longer.

The Portal's Application Features settings control registration, password reset, and whether email verification is required before application authorization. Disabling two-factor setup prevents new enrollments but continues to challenge users who already enrolled. Verification links opened after the application flow expires can still verify the account after a normal Portal sign-in; the user must then start a new application flow.

Application environments can add an email verification requirement, disable passkey login, configure separate social connections, or opt into SSO. An SSO session can be reused only by opted-in applications in the same organization and environment, expires after eight hours, and is checked against the source application's current access and settings. Password or MFA changes invalidate it. For accounts with MFA configured, a shared session is issued only after the application's Fortify two-factor challenge succeeds. Consumer sign-out is local to that consumer; it does not implement single logout across applications.

## Know when a new device signs in

The application detects sign-in attempts from unrecognized devices to protect users from unauthorized access to their accounts.

### Email notification for unrecognized devices

When an account signs in from a browser it has not used before, the owner receives an email describing the device, its address, and the time. The email includes a button that signs the new session out immediately.

Recognition is per account: a browser familiar to one account is still new to another. Devices are remembered whatever the alert setting says, so turning alerts on later does not re-report existing ones, and impersonation never counts as a sign-in. Users can also review and sign out devices themselves from the [security page](user-accounts.mdx).

To configure sign-in alerts:

1. In the admin panel, navigate to **Applications** and select the application.
2. Open **Users & authentication** and select the **Sessions** tab.
3. Turn **Email owners about sign-ins from unrecognized devices** on or off.
4. Optionally, set the **Support email** named in the alert. Without one, the alert points users at their password instead.
5. Select **Save**.

### Revoke sessions for unrecognized sign-ins

Users can revoke the suspicious session directly from the email notification. With a single click the session is revoked and the user is redirected to the unauthorized sign-in page, which confirms the device has been signed out. The button is a signed link that expires after a day and revokes exactly the session the alert names — never the session of whoever clicked it. After revoking, the affected device must sign in again.

When an application enables device binding for email verification, a verification link opened on a different browser is refused and shows the same page family: the attempt was cancelled and nothing was signed in there. Open the link on the device that requested it.

## Understand integration boundaries

OAuth userinfo, the management API, and user webhooks check application-environment boundaries and expose only their documented fields. These checks do not automatically scope every Portal feature or create separate databases. The `super_admin` role has global administrative access. Protect management and webhook secrets, and review all other endpoints before hosting mutually untrusted organizations. See [tenancy and OAuth](core-concepts.mdx) and [user metadata](user-metadata.mdx). User impersonation is sensitive: inspect the current model and policy checks before granting roles or relying on impersonation controls.

## Report a vulnerability

For vulnerability reports, use a private channel to reach the maintainers; no dedicated security contact is specified in the repository.
