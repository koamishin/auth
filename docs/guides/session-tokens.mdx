# Session tokens

When a user is signed in, the application can mint a **session token**: a short-lived JSON Web Token (JWT) that describes the user and their session. Backends verify one offline against the published JWKS document — no call to the portal per request.

A session token lives for **60 seconds**. Its job is to answer "who is this, and in what session, right now", not to store access; mint one whenever a request needs it.

## Default claims

Every generated token carries the claims below. They cannot be overridden.

| Claim            | Abbreviation expanded   | Description                                                                                        | Example                    |
| ---------------- | ----------------------- | -------------------------------------------------------------------------------------------------- | -------------------------- |
| `sub`            | subject                 | The ID of the user the session belongs to.                                                         | `123`                      |
| `iss`            | issuer                  | The portal URL. Matches the `issuer` in the discovery document.                                    | `https://auth.example.com` |
| `iat`            | issued at               | When the token was issued, as a Unix timestamp.                                                    | `1713158400`               |
| `nbf`            | not before              | The time before which the token is invalid. Equal to `iat`.                                        | `1713158400`               |
| `exp`            | expiration time         | The time after which the token is invalid — `iat` + 60 seconds.                                    | `1713158460`               |
| `jti`            | JWT ID                  | The unique identifier for the token.                                                               | `01J2X3...`                |
| `sid`            | session ID              | The session the token belongs to — see below.                                                      | `laravel-session-id`       |
| `azp`            | authorized party        | The `Origin` header of the minting request. Omitted when there was none.                           | `https://app.example.com`  |
| `v`              | version                 | The version of the session token.                                                                  | `2`                        |
| `fva`            | factor verification age | Minutes since each factor class was verified — see below.                                          | `[7, -1]`                  |
| `sts`            | session status          | The status of the session: `active`, or `pending` while it owes a verification.                    | `pending`                  |
| `tasks`          | pending tasks           | The verifications still owed, by name. Empty when `sts` is `active`.                               | `["mfa"]`                  |
| `application_id` | —                       | The application the token was minted for. Backends use it to refuse tokens for other applications. | `100`                      |
| `environment`    | —                       | The environment the token was minted for.                                                          | `production`               |

### The `sid` claim

For a browser-session mint, `sid` is the browser session's ID — the same identifier the management API lists and revokes, so a backend can correlate a token with a device and revoke it. For an SDK mint, `sid` is the access token's ID, the grant the token belongs to.

### The `fva` claim

`fva` reports `[first, second]`: the minutes since a first factor (password, passkey, emailed code, or social sign-in) was last verified in this session, and the minutes since a second factor (the two-factor challenge) was last verified. `-1` means never in this session.

Two consequences follow from "in this session":

- **Switching accounts resets it.** A factor verified for one account never vouches for another. See [multi-session accounts](multi-session.mdx).
- **Impersonation never vouches for the subject.** While `act` is present, `fva` reads `[-1, -1]`: those verifications belong to the impersonator.

SDK-minted tokens carry `[-1, -1]` too — the minting request holds an access token, not the browser session where verification happened.

### Organization claim

The **`o` claim** is included only when the session has an application context. Its value is an object with the application's organization and the user's role in it.

| Claim | Abbreviation expanded | Description                                           | Example |
| ----- | --------------------- | ----------------------------------------------------- | ------- |
| `id`  | ID                    | The ID of the organization.                           | `7`     |
| `slg` | slug                  | The slug of the organization.                         | `acme`  |
| `rol` | role                  | The user's role in the application, without a prefix. | `admin` |

### Actor claim

The **`act` claim** is included only while an administrator is impersonating another user.

| Claim | Description                                 | Example                    |
| ----- | ------------------------------------------- | -------------------------- |
| `iss` | The referrer of the token.                  | `https://auth.example.com` |
| `sid` | The session ID of the impersonated session. | `laravel-session-id`       |
| `sub` | The ID of the impersonator.                 | `456`                      |

## Mint a session token

### From a browser session

```
GET /session/token
```

For the signed-in session. The response:

```json
{
    "token": "eyJhbGciOiJSUzI1NiIs...",
    "token_type": "Bearer",
    "expires_in": 60,
    "expires_at": 1713158460
}
```

### From an access token

```
POST /api/oauth/session-token
Authorization: Bearer <access token>
```

For SDK-driven backends: exchange the access token a client application already holds from the authorization-code flow for a short-lived session token its own backends can verify offline. Only **user** access tokens qualify — client-credential (management) tokens have no user behind them and are refused.

Both client libraries wrap this endpoint:

```php
// Laravel
$token = Koamishin::sessionToken();
```

```ts
// Browser
const sessionToken = await koamishin.getSessionToken();
```

## Validate session tokens

Verification is standard JWT verification: check the signature against the JWKS document and validate `iss`, `exp`, and `nbf`. Any JWT library that understands JWKS works. The tokens are RS256; the header's `kid` matches the `kid` published for the key, so key rotation is handled the usual way.

JavaScript, with [`jose`](https://github.com/panva/jose):

filename: app/api/example/route.ts

```ts
import { createRemoteJWKSet, jwtVerify } from 'jose';

const jwks = createRemoteJWKSet(new URL('https://auth.example.com/oauth/jwks'));
const { payload } = await jwtVerify(token, jwks, {
    issuer: 'https://auth.example.com',
});
```

PHP, with [`lcobucci/jwt`](https://github.com/lcobucci/jwt):

filename: app/Services/SessionTokenVerifier.php

```php
$token = (new Parser(new JoseEncoder()))->parse($jwt);

(new Validator())->assert(
    $token,
    new SignedWith(new Sha256(), InMemory::file($publicKeyPem)),
    new IssuedBy('https://auth.example.com'),
);
```

The PHP SDK ships `SessionTokenVerifier`, which performs this verification with a cached key set, and `Koamishin::userForSessionToken()`, which adds the application binding — a token minted for another application is refused.

> Always bind the claims to your own application before trusting one. Check `application_id` and `environment` against your configuration, the same way the userinfo endpoint enforces them.

## Lifetime and revocation

- Tokens live **60 seconds**. Mint a fresh one per request or cache it until just before `exp`; do not store it.
- A revoked session does not retroactively kill tokens already minted — but their remaining life is under a minute. For current state, check `sid` against the management API's session endpoints.
- Banned users cannot mint; existing tokens for them age out within the minute.

## Not supported

- **Custom claims via templates** (Clerk's JWT templates) are not available. Large data belongs in [user metadata](user-metadata.mdx), fetched through the management API instead of packed into the token.
